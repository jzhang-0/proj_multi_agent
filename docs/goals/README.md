# 总控台 Goal 清单

本目录按领域拆分 Goal。此文件保存执行说明、完成契约、领域依赖和分卷索引;具体 Goal 在同目录对应领域文件中维护。

## 总目标

把全部 Goal 实现到 `[x]`,得到一个可用全局命令 `amux` 启动、以团队 Leader 为责任主体、让 human 能回看任务与验收证据的协作总控台。

**终止条件**:全部 Goal 为 `[x]` 且各自带 `验证` 与 `证据` 两行;剩余任何 `[ ]` 必须带 `进行中` 说明阻塞原因。不允许以「主要功能已完成」结束。

## 多 AI 并发执行说明

这是一个多 AI 协作仓库,成员同时也是开发者。规则(与 AGENTS.md 一致,冲突以 AGENTS.md 为准):

- 每个 AI 每次只做一个 Goal。开工前在该 Goal 下写一行 `处理登记`:模型、开始时间、分支名。
- 新开 worktree 开发,分支名规范:`<goal-id小写>-<模型>`,如 `bus-002-claude`。
- 做完 merge 进 `main`,没报错就算过;有冲突自己解决;合入后删分支、删登记,按完成契约补 `验证` 与 `证据`。
- 只要 Goal 没被认领、前置已满足,就可以做,记得先标记认领。
- 一台机器上有大量并发开发:**不要频繁跑测试**,只在必要时测,测试能轻量就轻量(单文件 pytest filter,不跑全量)。
- `处理登记` 只描述当前事实,不改变完成状态;空分支、过期分支不算进行中,下一个会话可清掉过期登记后认领。

### 执行顺序

1. **批 1:BUS + TMX**(可并行,两领域互不依赖)。收口于 **QA-002**:一条命令跑通「msg 入队 → 投递 → 假成员窗格收到」端到端并输出延迟数字。
2. **批 2:ROS**。收口于 `uv run roster up` 拉起全部真实成员并全员报到。
3. **批 3:CON**。收口于截图自验证(见 QA-004)+ 硬指标实测。
4. **批 4:GATE**。前置是人对 IM 平台拍板,没拍板前不开工。
5. **批 5:WS(多工作区)**。2026-08-17 human 拍板要做；实现范围收口于 WS-011。开工前先拿到 [工作区卷](workspace.md)「需要 human 拍板的」那四项答复。
6. **批 6:TEAM(团队协作)**。先保存并绑定团队档案，再建立任务账本；不得用自由文本群聊替代责任、验收或接管记录。
7. **发布工程(REL)**。发布候选必须先用构建出的 wheel 在源码仓库外完成隔离安装与 smoke；上传 PyPI 是独立的外部发布动作。

8. **批 7:WEB(Web 控制台)**。2026-08-30 human 拍板：路线 B，与 TUI 并列全功能对齐。主线 WEB-001→004，之后按前置并行，WEB-009 收口；见 [Web 控制台卷](web.md)。

批 1 没收口前不要开批 3(console 依赖 bus/tmuxctl 的接口)。

### 视觉自验证

步骤、取证命令与判定清单见 [视觉自验证](../quality/visual-check.md);下面是要点。

TUI 类 Goal(CON 卷)必须**自己看画面**再判断:把 console 跑在 tmux 会话里,`tmux capture-pane -p -e` 取带颜色的画面(或 Textual 的 SVG 导出),用读图/读文本确认布局、配色、对齐,不允许「代码写完就算画对了」。每次操作后重新截取,不凭上一张推断。判断不了的审美问题(首版配色、布局取舍)标「需人工」交 human 点头。

**界面类 Goal 至少要有一轮对真实数据源的全流程取证**(2026-08-30 立，起因见下)。fixture、Demo 数据、合成帧只能用来覆盖分支和做回归基线，**不能作为「这个界面能用」的唯一证据**:

- Web 类:用**真实浏览器**打开**真实运行的成员/工作区**，把要交付的路径从头走一遍(打开→选中→交互→退出)并截图;不能只跑 Playwright 对着 Demo fixture 截一张。
- TUI 类:同理,对着真实成员会话取画面,不是只看 QA 合成快照。
- 合成帧与真实帧的差别正是最容易漏的一类缺陷:渲染错位、鉴权在真实 cookie/票据链路上失败、真实尺寸下的换行——这些在 fixture 下全都「看起来是对的」。WEB-007 就是这么漏的:视觉自验证只用了 Demo fixture 与合成帧，human 用真实浏览器一开就撞到镜像帧渲染错位与终端 4401(T-025)。
- **评审者同样受这条约束**:证据里只有 fixture/合成帧时，不能判通过;要么要求补真实数据源的一轮，要么在通过意见里写明"未做真实数据源验证"这一未覆盖面，不能默认它等价。

配套要求:服务端对 WS 拒绝(4401 等)必须留下可查日志,否则真实环境里出问题只能看到浏览器一句 close，无从定位。

### 已知陷阱

- 系统 python 是 3.8(miniconda),项目要求 ≥3.11:一律 `uv run`,不要直接 `python3`(`uv` 已于 2026-08-16 由 human 安装)。
- `tmux send-keys -t` 不接受 `=name` 精确匹配语法(has-session 接受),用普通会话名(v0 已踩过)。
- TUI 程序(含成员的 CLI 和 console 自己)输出流全是 ANSI 重绘序列,不要拿 pipe-pane 原始流做语义解析,活性检测只看"有无输出",语义走总线消息。
- 多个 worktree 共享同一个 `bus/` 运行时目录会互相干扰:测试一律用临时目录注入路径(BUS-001 要求路径可配置),不碰仓库根的 `bus/`。
- 成员正在输入框有半行字时注入消息会拼接污染:v0 已知问题,TMX-003 处理。
- IM 平台选型、sqlite 迁移这类未决项停下来问 human；产品范围变更必须由 human 直接拍板。

## 完成契约

一个 Goal 只有同时满足以下全部条件才可以改 `[x]`:

1. 实现已合入 `main`,Goal 描述中列举的**每一项**都已实现(枚举是完整清单,不是示例)。
2. 有覆盖列举项的自动化测试(TUI 视觉类可用 QA-004 的截图证据替代),本地通过。
3. 有一条任何人可重复执行的验证命令。
4. 受影响的文档已同步(架构决策、运行时 prompts、AGENTS.md、README)。
5. 实际依赖的前置 Goal 已 `[x]`(按具体 Goal 判断,不按整个领域收口判断)。

**禁止**:stub/占位/`TODO` 声明完成;跳过或注释测试声明完成;改窄 Goal 描述声明完成(要缩范围就拆新 Goal 并记入 changes.md);「第一阶段完成」;没实际运行验证命令就填证据。

未完成的 Goal 保持 `[ ]` 并追加 `进行中`:写清已完成部分、未完成部分、阻塞原因,供下一个会话接手。没有 `进行中` 的未完成 Goal 视为无人认领。

完成格式:

```text
- [x] **BUS-000** — (示例)……
  - 验证:uv run pytest tests/test_policy.py -q
  - 证据:src/bus/policy.py;tests/test_policy.py 覆盖去重/限频/熔断三分支
```
