# 产品定义 — 总控台

一句话:**一台机器上由 Leader 负责、多个 AI 协同执行的可追责团队总控台**；人只需面向 Leader，仍能从一个 TUI 看见全部任务、证据与过程。

## 背景与现状

仓库里已有可用的最小总线(v0):`hub.py` 轮询 `bus/queue/` 把消息用 `tmux send-keys` 注入收件人终端,`msg` 命令供人和 AI 发言,`start.sh` 拉起成员。它已实测跑通互相 @，但这只是协作的**沟通通道**，不是产品的主模型。总控台要把这条通道提升为可分派、可验收、可追责的团队协作系统。

## 目标形态

一个命令启动的全屏 TUI(命令名 `amux`,原工作名 `console` 保留为别名),布局:

```
┌──────────────┬─ 任务与证据 ────────────────────────┐
│ Fable  Leader│ T-024 登录页修复 · 验收中           │
│ 对 human 负责│ 负责人:Fable  执行:Sonnet           │
├──────────────┤ 证据:测试 42 passed · 截图 2 张      │
│ 进行中  3    │ 评审:Opus 退回 · Leader 已接管       │
│ 待验收  1    │ 事件流:派工 → 提交 → 退回 → 接管    │
├──────────────┤                                      │
│ 成员状态      │ 选中成员时,这里可换成终端画面        │
├──────────────┴──────────────────────────────────────┤
│ > 请 Fable 推进登录页问题_                          │
└───────────────────────────────────────────────────┘
```

左侧首先是**团队与任务状态**，右侧首先是**任务看板、任务详情和不可覆盖的事件流**；成员终端镜像和群聊是可切换的辅助视图。输入框在底部通栏。

- **团队**:每个团队恰有一名 Leader；Leader 直接面向 human，负责拆解、分派、推进、验收与最终结果。首个默认团队为 `fable-core`：Leader 是 Claude Fable 5 / high，成员是 Sonnet / xhigh、Opus / high、Luna / high-fast、Sol / xhigh。
- **任务账本**:每项任务都记录 Leader(最终负责)、执行者、评审者、状态、证据与全量事件。成员可以推进、提交和评审，不能自行最终结项。
- **主画面 · 协作事件流**:派工、进展、阻塞、提交、评审、退回、验收、重新分派和接管都以结构化事件上屏，可按任务回看。
- **主画面 · 成员画面**:实时镜像该成员的终端(看它正在干什么),不用切出去 attach;打开时把它的 tmux 窗口调成主画面大小,让它自己重排铺满;PgUp/PgDn、Ctrl+↑/Ctrl+↓ 和滚轮通过 `capture-pane` 翻它自己的 tmux 回滚区,不切进 copy-mode。
- **输入框**:human 默认对 Leader 说话。Leader 对成员下达任务或请求评审；成员的普通进展和证据归入任务，不把每次协作降格为群聊。成员直连仍可用于必要的终端操作，且每个动作进入审计；输入为空时 Delete/Backspace、Forward Delete、Enter 和 Shift+Tab 可作为独立按键透传，输入不为空时删除键只编辑本地文字。
- **群聊**:保留为一种关联沟通渠道，承载讨论、澄清与临时广播；它不能代替任务归属、评审、验收或接管记录。
- **控制操作**(对选中成员):软打断(Esc/Ctrl-C)、终止、重启、全屏接管(attach)。

## 责任与接管

任务的标准路径是：**Leader 建立/拆解 → 分派成员 → 成员执行并提交证据 → 评审或退回 → Leader 验收 → 向 human 汇报**。

- Leader 可以自己实现，也可以指定另一名成员评审；无论谁写代码、谁评审，Leader 都对最终结果负责。
- 如果成员反复无法完成，Leader 可发起“接管”。接管事件必须记录原因、接管范围、原成员已交付内容和后续验收方式；既有记录不可删除或改写。
- Leader 接管后可以让原成员继续协助、改派给其他成员，或亲自完成；最终状态仍由 Leader 验收并向 human 说明。

当前已完成的群聊和终端控制能力在过渡期间保持可用；团队档案先落地，任务账本与以 Leader 为唯一人类入口的交互在 TEAM-002 实现。

| 指标 | 预算 |
|---|---|
| 消息入队 → 注入收件人终端 | P95 < 200ms |
| 消息 → 时间线上屏 | < 200ms |
| 成员详情画面刷新 | < 100ms(活跃窗格) |
| 键入回显 | 不掉帧(单帧 < 16ms) |

## 设计原则

1. **tmux 是唯一控制通道**。不逆向任何 CLI 的内部接口,成员对总控台零感知、零配合要求;任何新 CLI 只要能跑在终端里就能加入团队。
2. **总线契约冻结**。`./msg` 的命令行接口和消息 JSON 结构是成员依赖的公共契约,只能向后兼容地扩展(见架构决策 §3)。
3. **防环在传输层**。去重、限频、积压熔断由总线强制执行,不依赖模型自觉(借鉴 `reference/pi-extensions/src/talk/policy.ts` 的结论)。
4. **人永远优先**。人的消息不受限频约束,人的打断立即生效。
5. **责任不可漂移**。任务无论如何分派、退回或接管，始终能追溯到唯一 Leader；日志只能追加，不能用群聊摘要替代证据。

## 多工作区(2026-08-17 human 拍板要做)

`amux` 是装在机器上的工具,不是只服务自己这一个仓库。**一个「工作区」= 一个被 amux 服务的项目目录,每个工作区有自己的一组成员,多个工作区可以在一台机器上并存。**

- 成员进程跑在所属工作区的项目根,不是 amux 仓库。
- 会话名带工作区命名空间,所以 `claude` 可以同时在多个项目里各跑一份。
- 每个工作区有独立的总线运行时(队列、审计日志、ask/reply),互不串台。
- 工作区内部的寻址方式不变:成员之间仍然 `msg claude`,短名在边界层解析到本工作区。
- 在某个目录敲 `amux`,就在**这个目录**里工作(未登记则自动登记);不会跳到 amux 自己的仓库。
- 成员不默认四个。仓库根 `roster.toml` 只是预设,工作区用 `amux member add|rm` 自己增减。
- 工作区可绑定一个保存于 `~/.amux/teams/` 的团队档案；档案说明 Leader、成员、模型偏好、职责及经验证的启动适配（含环境变量）。默认 `fable-core` 的 Claude 系列由 `claude` 启动，关闭 alternate screen 以让 tmux 保留可供总控台回看的历史，并以空 `NO_COLOR` 避免 amux 调用环境意外关闭成员颜色；Luna/Sol 由 `codex` 启动；Cursor `agent` 只有在另行配置 Cursor 自有模型时才会加入名册。

工程拆分见 [工作区 Goal 卷](../goals/workspace.md)。原「一个仓库一组成员」的形态是它的单工作区特例。

## 远期(本期不做,但架构要留口)

- IM 网关:手机端作为 human 与 Leader 的沟通入口；群聊仍可作为关联讨论渠道，`docs/goals/gateway.md` 占位,IM 平台选型是人的决策。
- 跨机器成员。

## 明确不做

- Web 界面、GUI 应用(本期只做 TUI)。
- 替代各 CLI 自己的会话管理/历史(总控台只管消息与控制,不管成员的对话内容存储)。
- 任何绕过各 CLI 权限机制的"自动点确认"(权限用各家的配置放行,见 roster)。
- 把自由文本群聊当作任务归属、验收或责任的唯一记录。
